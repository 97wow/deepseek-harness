# Agent Note: Mythos 项目管理文档

Status: implemented

[English](2026-08-25-mythos-project-management-documents.md) | 中文

## Problem

仓库已深入记录 DeepSeek Harness 架构、子系统约定、贡献者工作流和决策，但 `products/mythos-agent/` 没有产品入口。维护者必须从源码、本地评测数据、产物和提交历史中重建 Mythos 使命、产品模块、Desktop 归属、里程碑顺序、证据化进度、开发规则和发布缺口。

通用仓库文档不能拥有可变的 Mythos 路线图或进度视图，因为这些事实只属于一个产品，并且与可复用 Harness 约定独立变化。生成的评测报告是测量真源，但不解释项目优先级、未完成集成或下一个已接受工作包。

## Decision

`products/mythos-agent/README.md` 是产品入口，并链接 `products/mythos-agent/docs/` 下的产品级项目管理文档组。该文档组借鉴 TheArcher 项目记录中有价值的分工，将愿景与原则、产品与 Desktop 架构、模块归属、路线图、进度、开发规则和评测/发布策略分配给独立文档。

产品进度看板是工作项状态与执行顺序的唯一维护解释。版本、配置、评测用例、生成测量、发布检查和总控策略仍以可执行源为真源；看板链接这些所有者并记录证据日期，不替代它们。

项目级文档组面向项目所有者使用简体中文维护。产品 README 在现有配对约定下保持完整双语。持久 Harness 架构和包约定仍属于仓库文档层级，项目文档只链接而不复制。

## Ownership and updates

- 产品范围或原则同时更新愿景页与可执行项目模型。
- 组合、Desktop 托管或目录职责变化时更新架构与模块地图。
- 已接受的未来范围先进入路线图，再成为进度工作项。
- 工作项只有在所述验证存在后才进入完成；生成评测数据仍是数值真源。
- 评测、发布、安全或 Git 工作流变化时，开发规则和质量页与自动化同步更新。

## Alternatives considered

**将所有内容放入产品 README。** 单一长页会混合入门、当前状态、架构、策略和计划，使频繁变化的进度编辑难以评审，并掩盖面向消费者的产品约定。

**只使用源码和生成报告。** 这些真源能准确描述机制和测量，但不拥有项目意图、里程碑依赖、已接受缺口或执行顺序，因此每个维护者都必须重复重建同一项目模型。

**将 Mythos 状态加入仓库级架构文档。** 这会把单一产品的可变实现状态混入持久 Harness 文档，并违反仓库每个事实只有一个所有位置的层级。

## Consequences

Mythos 获得稳定的文档入口和显式维护规则，而不复制 Harness 子系统文档组。产品变更需要在所属项目页与进度看板承担少量文档成本，而生成指标与可执行策略仍保持权威。中文项目管理页不在仓库级翻译配对门禁范围内，因此评审者必须显式检查其链接与当前事实的准确性。
