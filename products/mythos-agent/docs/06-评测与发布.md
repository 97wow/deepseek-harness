# 评测与发布

## 评测分层

| 层级 | 目的 | 当前内容 | 主要门禁 |
|---|---|---|---|
| 单元与约定 | 验证产品代码、配置、安全和数据处理 | Product、Evaluation、Flywheel、Release、Controller 和 Desktop 的所属测试 | 产品 `test`/`typecheck`/`typecheck:control` + Desktop `test` |
| Release suite | 快速证明基本任务完成与安全 | 精确文件、缺陷修复、凭据隔离、跨文件约定、只读诊断 | `gate` |
| Product suite | 覆盖更复杂的工具、范围与证据行为 | 并发去重、安全路径、大工作区、失败恢复、无操作证据 | `gate:comprehensive` |
| Journey | 验证多轮会话与冷恢复 | 3 阶段真实实现任务 | `gate:journey` |
| Advanced journey | 验证压缩与并行 subagent | 压缩连续性、两个并行子 agent 与父级集成 | `gate:advanced-journey` |
| Real repository | 验证真实仓库、固定修订、受限路径与未来测试 | DSH Session 持久化性能修复、PowerShell prompt 碰撞修复 | `gate:real-repo-scope` 当前只强制第一例 |
| M3 release smoke | 验证发布闭包的模型、persona、工具和后续请求协议 | 本地 HTTPS mock 检查 25 个工具 schema、`read` 工具调用/结果关联、交互式恢复和敏感值不泄漏 | `release:verify` 内的打包 consumer |
| Server dataset | 检查服务端飞轮数据健康与覆盖 | 原始身份、内容、证据、计费和使用量统计 | `flywheel:server:gate`，当前未进入 `release:verify` |

## 外部验收原则

评测 agent 不决定自己是否通过。每个用例在隔离工作区准备输入，Agent 执行后由 TypeScript verifier 检查文件字节、受保护文件、测试退出码、隐藏用例、路径范围、会话事件和工具证据。

执行结果的 `passed` 只由 verifier 输出。Agent 最终文本、进度语气、代码 diff 存在性或工具调用数都不能单独证明任务成功。

## Cohort 身份

```text
DSH version
  + Mythos version
  + effective evaluation configuration SHA-256
  + mode / overlay identity
  = cohort prefix
```

门禁对每个用例使用 `cohort prefix + case id` 定位样本。下列任意变化都使原 cohort 失效：DSH 版本、Mythos 版本、Profile/Overlay 内容、用例语义、执行入口或受验运行时。

## 发布门禁

`pnpm --dir products/mythos-agent release:verify` 按顺序执行：

1. 产品单元与约定测试。
2. 产品 TypeScript 类型检查。
3. Web 表面冒烟测试。
4. 将本地运行和会话建立为内容寻址飞轮归档。
5. 生成 cohort 比较分析。
6. 验证 release suite、comprehensive suite、journey、advanced journey 和当前已指定的 real-repo scope。
7. 验证产品 Profile、已构建 DSH CLI、固定版本、跟踪文件密钥策略、本地 `.env` 权限和展开配置。
8. 单独类型检查发布代码，从固定 lockfile 构建自包含闭包，产生两个字节一致的独立 staging 归档。
9. 在干净临时目录验证完整性清单，冒烟 Headless/Web/M3/交互式 CLI，并使用篡改负向探针证明完整性检查会拒绝变更。

发布门禁当前不运行 `flywheel:server:gate`，也不强制 `dsh-pwsh-prompt-collision`。当前实际 checkout 还没有 `flywheel/data/comparison.json`，因此本文档不声明当前付费 cohort 通过。这些证据被刷新且两个门禁缺口被明确接受、纳入或删除前，不应对外声明“所有真实仓库与服务端数据门禁均已通过”。

## 打包约定

`pnpm --dir products/mythos-agent release:pack` 先运行发布检查，再离线安装固定 lockfile、构建 Mythos Web 前端、部署 DSH 生产依赖并将工作区符号链接收口到 staging 树内。两个不同临时目录生成的归档必须字节完全一致；最终文件名包含 Mythos 版本和 12 位提交 ID，同时生成 SHA-256 文件。

发布包必须包含启动入口、Headless/Web Profile、Mythos Agent Preset、DSH 运行时、Web 静态资源与 `release-integrity.json`；必须拒绝 `.env`、`runs/`、`sessions/`、`flywheel/data/`、越界符号链接和构建机绝对路径。打包与消费端验证不等于已签名、已 Notarize、已发布或已安装。

## 评测失败处理

1. 先固定失败 cohort、case id、原始会话、verifier 证据和运行时状态，不立即改提示词。
2. 将失败分类为环境、模型、工具、状态/上下文、范围、验证、协作或用例本身问题。
3. 只有当同类失败能稳定复现，且修复面对实际产品机制时才改代码。
4. 修复后先跑聚焦用例，再按门禁所需样本数重新采样；新 cohort 完全通过前不替换发布证据。

## 完成定义

一个 Mythos Agent 产品变更只在以下条件同时成立时完成：

- 行为改动存在外部可观测的验收，并覆盖至少一个失败路径。
- 新行为通过真实产品入口执行，不只在 mock 或一个未装配的类中存在。
- 受影响的评测 cohort 有足够样本，通过率、超时率、原始覆盖与行为指标满足所属门禁。
- 凭据、运行数据与用户状态不进入发布包，打包产物可重现且可校验。
- 所属文档、进度看板和必要的 Agent Note 已同步，所有实际运行的检查已记录。
