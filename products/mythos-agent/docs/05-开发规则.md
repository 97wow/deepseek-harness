# 开发规则

## 指令优先级

开发 Mythos Agent 时先遵守仓库根 [`AGENTS.md`](../../../AGENTS.md) 与所在子树的 `AGENTS.md`，再遵守本文档的产品规则。通用 DSH 行为应在 `packages/` 的所有包中实现；仅 Mythos 的组合、评测、飞轮、发布或治理行为才进入 `products/mythos-agent/`。

## 开发前检查

1. 确认任务类型：诊断、评审和状态任务不修改文件；实现任务才获得写权限。
2. 查看 [`04-进度看板.md`](04-进度看板.md) 与 [`03-路线图.md`](03-路线图.md)，确认工作项、当前里程碑和退出标准。
3. 查看 `git status` 和相关 diff，保留用户变更，不使用广泛暂存或破坏性恢复命令。
4. 确认改动属于产品层还是 DSH 通用层；当两个产品可能需要同一机制时，先评估 capability seam 或通用包，不在 Mythos 内复制。
5. 如果改动非局部或纯机械，在同一变更中添加或更新 Agent Note，并更新所属文档。

## 产品代码边界

- `product/` 只拥有源码/发布启动、交互式会话包装、产品配置验证和表面冒烟，不实现 agent loop。
- `home/` 只拥有可发布的 Profile、Preset 和默认空状态，不跟踪用户凭据、会话、工作区注册或本地设置。
- `eval/` 拥有用例、配置身份、执行快照和外部 verifier，不以模型文本“看起来正确”判定通过。
- `flywheel/` 拥有归档、分析、筛选和门禁策略，原始数据与派生数据必须保持可区分和可追溯。
- `release/` 从固定 lockfile 构建可验完整性的自包含运行闭包，并在仓外消费端验证；发布流程不更写源 Profile 或重录评测。
- `control/` 只拥有战略项目状态和决策，不得依赖文件编辑、Shell、任务执行或产品工具 registry。
- `apps/desktop/` 只拥有 Electron 托管、用户展示、受管服务路由、签名热配置、应用更新和 macOS 打包，不在桌面壳中 fork DSH 或 Mythos 产品逻辑。

## 配置规则

1. Headless 和 Web 必须保持同一模型 provider、model、reasoning、persona 与核心 Agent Preset。
2. 模型、网关、上下文窗口或输出上限变化时，必须更新配置同一性测试并生成新 cohort，旧评测不得证明新配置。
3. 发布 Profile 不接受用户 Preset、插件界面或模型选择改变产品身份；需要可配置产品时先定义独立版本化策略。
4. 产品运行只从环境读取凭据，不在 Cordis YAML、打包产物、日志、会话或评测工作区中写入真实密钥。
5. 展开后的 Cordis 配置是组合证据；发布前必须验证必需模型名、Preset 和 persona 实际出现在 dump 中。

## 评测规则

1. 每个用例定义任务、隔离 setup、外部 verifier、能力维度与层级；提示词不得包含 verifier 的隐藏结果。
2. 受保护的测试、fixture 和范围限制由 verifier 独立检查，不相信 agent 声明。
3. 修改任务必须记录修改后验证；无操作任务必须证明源码和测试未变。
4. 重复评测在一个正式运行中使用同一不可变执行快照；执行期间的源码漂移必须导致失败，不得静默重算身份。
5. 评测超时、基础设施错误、模型错误和 verifier 失败必须分类记录，不合并为一个无信息的“failed”。
6. 发布通过率只读取与当前 DSH 版本、Mythos 版本、配置哈希和模式完全一致的 cohort。

## 数据与安全规则

- 飞轮原始数据可以包含对训练与诊断有价值的原始身份和内容，但必须位于受控存储，不得提交、打包或输出到普通日志。
- 归档索引保存内容哈希与原始存在性；缺失原始会话的 label 不得满足原始覆盖门禁。
- 发布扫描只输出命中的策略名，不回显可疑密钥值。
- `.env`、`home/sessions/`、`home/storages/`、`runs/`、`flywheel/data/` 和 `dist/` 的运行内容不得进入 Git 发布范围。
- Desktop 只接受小型、无 userinfo 的 HTTPS 端点列表；热配置在解析路径前必须通过签名，每个资产必须通过大小和 SHA-256 校验，激活指针使用 0600 权限原子替换。

## 变更验证

| 变更 | 最小验证 |
|---|---|
| 文档 | `pnpm run doc-sync`、`pnpm run lint`、`git diff --check` |
| Product 启动或配置 | 产品 `test`、`typecheck`、`smoke:web`、`release:check`；交互式变化还需要发布包 consumer 冒烟 |
| 评测入口、用例或 verifier | 产品 `test`、`typecheck`，以及受影响的真实评测与重复采样 |
| Flywheel 归档或分析 | 产品 `test`、`typecheck`、`flywheel:build`、`flywheel:analyze` 与相关门禁 |
| Release | `release:verify`，确认新包通过完整性清单、仓外 Headless/Web/M3 消费端与篡改负向探针 |
| Desktop | `npm --prefix apps/desktop test`；打包变化使用已验证 `MYTHOS_RUNTIME_ROOT` 运行 `pack:mac`，签名/更新变化还需真实产物和渠道冒烟 |
| Controller | 产品 `test`、`typecheck:control`，装配变化还需真实决策链路冒烟 |

只运行与改动表面相匹配的检查；真实模型评测会消耗 API 额度，不因文档或无关代码变化重跑。

Desktop 签名构建必须先将发布包内部绝对链接改写为发布根内的相对链接，并拒绝越界链接；签名顺序和原因见 [Desktop 运行时签名决策](../../../.agents/notes/implemented/bug-fix/2026-08-25-desktop-runtime-code-signing.zh.md)。Developer ID 与 Notarization 凭据只通过环境或系统钥匙串注入。验收同时检查严格代码签名、Stapler、Gatekeeper、DMG/ZIP 完整性，以及分发副本启动；本地通过不等于远程渠道已发布。

## Git 与完成定义

- 提交前使用 `git status`、`git diff` 和 `git diff --cached --check` 检查范围，只暂存本工作项路径。
- 不提交凭据、运行会话、本地飞轮数据、临时工作区或不确定发布产物。
- 完成一个自然检查点后创建小而聚焦的 conventional commit，测试与文档证据一起交付。
- 任务只在代码、失败路径、证据、文档和进度看板一致时完成。
