# 路线图

## 执行机制

1. 每个里程碑只有一个主要目标，优先完成一条可运行、可验收的端到端链路。
2. 完成必须同时满足产品行为、安全边界、回归证据和文档同步，不以“代码已写”代替验收。
3. 新抽象需要至少两个真实用例；性能优化需要测量数据；新提示词规则需要证明 harness 机制无法更稳定地表达。
4. 任何改动配置、用例或执行时身份的实验都创建新 cohort，不与旧 cohort 合并统计。
5. 连续迭代没有接近出口标准时，先缩小问题或回到可区分的评测，不继续增加规则、工具或编排层。

## M0：产品化基线（完成）

目标：将 Mythos Agent 从通用 DeepSeek Harness 中分离为可独立启动、评测和打包的产品。

- 建立 Headless 与 Web 产品 Profile。
- 固定 Agent Preset、persona、单模型身份与受控网关。
- 建立产品配置同一性测试、Web 冒烟测试和确定性打包。
- 固定 DSH 上游版本、提交与发布安全边界。

退出标准：Headless/Web 使用同一产品身份，产品可从已构建 DSH 启动，发布检查能拒绝配置漂移、凭据和非确定性产物。

## M1：可重现评测与飞轮基线（完成机制）

目标：建立不依赖模型自评的任务验收系统，并保留每个结论的原始证据。

- 建立发布用例、产品用例和重复采样。
- 建立执行快照、严格入口、内容哈希与来源校验。
- 建立原始会话归档、cohort 分析、服务端数据导入与筛选。
- 建立通过率、超时率、原始覆盖率、修改后验证率与时延门禁。

退出标准：评测能将运行快照、响应所有的模型与计费身份、原始会话和外部 verifier 结果绑定到一个不可变样本，门禁只读取完全匹配当前版本、配置与 variant 的 cohort。每个发布的付费样本门禁在 M2 持续刷新，不与机制交付混为一项。

## M2：真实复杂工程基线（进行中）

目标：证明 Mythos Agent 在多轮、压缩、冷恢复、subagent 协作与真实代码库中仍能完成任务。

- 将普通旅程、压缩连续性和并行 subagent 纳入重复采样门禁。
- 扩展真实仓库用例，覆盖不同编程语言、构建系统、仓库规模和受限修改。
- 建立失败分类，区分模型推理、工具使用、上下文、范围、验证、协作和基础设施故障。
- 将所有对外声明的真实仓库用例纳入门禁，不保留“已实现但不影响发布”的模糊状态。

退出标准：每个已承诺任务族都有多样本、原始会话和隐藏验收；主线 cohort 连续通过；失败能映射到一个可操作的 harness 改进面。

## M3：总控治理闭环（内核完成，装配待办）

目标：将已实现的决策内核装配为可审计、不执行任务的项目治理层。

- 定义真实 ProjectReviewSource、ControllerPort 与 Lead 边界。
- 持久化项目修订、决策、证据要求和运行状态，不记录密钥或执行原文。
- 将无已验证进展、重复失败、预算耗尽、原则冲突和目标漂移转为暂停与重规划决策。
- 建立“总控无工作工具”的组合级验证，而不只是 TypeScript 接口约束。

退出标准：一次真实项目阶段能从状态快照进入总控决策，再将可审计指令送达 Lead；总控无法访问文件、Shell 或执行任务。

## M4：发布与运行闭环（进行中）

目标：让已验收的 Mythos Agent 可安装、可升级、可回滚并可观测。

- 维持冻结 lockfile、自包含 DSH/Web 运行闭包、完整性清单、双 staging 确定性和仓外消费端冒烟。
- 完成 MYTHOS Desktop 受控服务路由、签名热配置、分层应用更新、Developer ID 签名与 Notarization 闭环。
- 建立发布渠道、安装、升级、回滚与发布后健康验收，同时保留 CLI 与 Desktop 的版本对应。
- 建立有界日志、错误分类、使用量、成本、任务完成和恢复指标，并将发布后失败安全回流到飞轮与回归用例。

退出标准：一个新版本能从干净仓库生成签名且可验完整性的 CLI 与 Desktop 产物，通过指定渠道安装，恢复现有用户会话，并在发生严重回归时回滚到上一个已验收版本。

## 暂不排期

- 无评测需求的多模型自动路由。
- 独立通用 agent 平台或与 DeepSeek Harness 重叠的能力层。
- 只为提升某个单次分数而增加的 prompt 优化。
- 在数据证明需求前引入分布式评测调度、消息队列或多集群控制面。
